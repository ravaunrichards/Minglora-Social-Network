# Minglora Social Network

**Minglora** is an independent social-networking application with a responsive browser interface and a Node.js HTTP API. It uses original branding and does not claim affiliation with Facebook or Meta.

## Data integrity: no seeded or demo content

A new installation starts with an empty database. The application does **not** generate example users, sample posts, pretend reactions, fake messages, placeholder groups, invented notifications, or fabricated engagement counts. Visitors must register and create real content before these areas contain records.

When the server opens a database created by an older version, it removes only the specifically identified legacy sample accounts and the records attached to those accounts. Other user records are preserved. Automated tests run against a separate temporary data directory and do not modify the app's normal data.

## Features included in this repository

- Responsive social feed and post composer
- Account registration, sign-in, sign-out, signed session cookies and password hashing
- User profiles and profile editing
- Post reactions and comments
- Friend requests and friend lists
- Group creation, browsing and membership
- Direct-message conversations
- Notifications generated by supported social actions
- Search across people, posts and groups
- JSON-backed persistence for a single running application instance
- Integration tests, Docker packaging and GitHub Actions CI

Only features implemented by the current code are described here. Stories, media uploads, password reset and email verification are not presented as working features until they have been implemented and tested.

## Requirements

- Node.js 20 or newer
- Docker and Docker Compose are optional for containerized local running

## Run locally

```bash
cp .env.example .env
npm start
```

Open http://localhost:3000. On first start, Minglora creates an empty data store in `data/db.json`. Register an account through the sign-up screen; there is no default account or shared password.

For persistent sessions across restarts, set `SESSION_SECRET` in your local `.env` file to a random secret of at least 32 characters. A development-only random value is generated if you leave it blank, which means sessions will be invalidated when the server restarts.

Generate a strong value with Node.js:

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

## Run the automated tests

```bash
npm test
```

The integration test starts an isolated server with its own temporary data directory and removes that directory after the test. It does not seed the app's normal data store or delete real user records.

## Docker Compose

Set a strong `SESSION_SECRET` in your shell or a private local `.env` file, then run:

```bash
docker compose up --build
```

The Compose service mounts a named volume at `/app/data` so app records persist when the container is recreated. Do not commit `.env` files, session secrets, database files, or production credentials.

## API overview

All application API endpoints are prefixed by `/api`.

- `GET /api/health`
- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`
- `GET /api/feed`, `POST /api/posts`
- `POST /api/posts/:id/reactions`, `POST /api/posts/:id/comments`
- `GET /api/users`, `GET /api/users/:id`, `PATCH /api/users/me`
- `POST /api/friends/:id/request`, `POST /api/friends/:id/accept`
- `GET /api/groups`, `POST /api/groups`, `POST /api/groups/:id/join`
- `GET /api/messages`, `POST /api/messages`
- `GET /api/notifications`, `GET /api/search?q=...`

## Deployment and production requirements

This repository contains a working application that can be run locally or in a container. **A publicly deployed website has not been verified by this repository change.** No production domain or hosting account is assumed.

Before accepting public users, use a persistent writable data volume and strong server-side secrets, configure HTTPS, backups and monitoring, and perform a security/privacy review. The current JSON store is intended for a single application instance; it is not suitable for multi-instance scaling. A larger public launch should migrate persistent data to a transactional database with migrations and appropriate access controls. Rate limiting, CSRF protection, email verification, password reset, content reporting/moderation, and secure media uploads also need implementation before describing the service as production-ready.

See [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) and [SECURITY.md](SECURITY.md) for operational guidance.
