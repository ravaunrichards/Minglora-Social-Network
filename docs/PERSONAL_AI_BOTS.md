### HR relational persistence checkpoint — 2026-11-12

- Added staged migration `supabase/migrations/20261112180000_minglora_ai_bot_hr_relational_persistence.sql` defining seven relational HR tables: departments, job-position catalogue, vacancies, candidate applications, appointments, employment history and HR audit logs.
- Seeded all 20 corporate position definitions. Department, vacancy, application, appointment and employment rows are owner-scoped; relational foreign keys, uniqueness, bounded checks and lookup indexes are included. Tables use RLS and revoke all access from `PUBLIC`, `anon` and `authenticated`; only the current server `service_role` receives direct table and RPC grants.
- Added owner-gated gateway operations `ai_bot_hr_state_upsert` / `ai_bot_hr_state_list`, and server callbacks. Existing HR Admin API read/write routes now load and persist the normalized HR state. A failed relational write rolls back the HR mutation before success is returned.
- Backward compatibility is preserved: if and only if the gateway explicitly reports `AI_HR_SCHEMA_NOT_READY`, reads stay on the existing runtime-state store and writes continue through the existing durable runtime-state save. Other database failures do not silently fall back.
- SQL additionally requires each application/appointment to reference an AI identity owned by the designated administrator and classified as `organizational`; appointment candidates must still be in the `created` (disabled) identity lifecycle and appointments are constrained to empty permissions, `not_granted` and `unchanged_disabled`.
- Added four schema/gateway tests and three HR API tests for full-snapshot persistence, relational readback, failure rollback and legacy fallback.
